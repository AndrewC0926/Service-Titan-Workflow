# NetSuite sold-projects vs. Scout board — backtest, 2026-09-10

Read-only. Nothing here writes anywhere. Source data: the real NetSuite
exports checked directly against this repo's importer (`ScoutSalesOrderLinesResults612.csv`,
152,988 rows; `ScoutResults653.csv`, 7,093 customer rows — see
`app.importers.netsuite_customers`) against a snapshot of Scout's own
`projects`/`signals`/`retrofit_buildings` tables (441 projects, 785 signals,
570 project-signal links, 60,166 retrofit buildings).

**Result, accepted as real:** 0 of 1,359 NetSuite equipment-sold projects
over $100k match a Scout project by exact normalized name. The two
populations barely overlap, and the reason is structural, not a matching
defect — see §4.

## 1. Method

**NetSuite side.** A "project" is the text after the customer name on a
sales-order line's `Name` field (`"<ID> <customer> : <project>"` — see
`app.importers.netsuite_customers`'s own docstring for the export's
quirks). Every order line was decoded and resolved to its customer: a
direct row's leading number is the customer's NetSuite **"ID"** field (not
Internal ID — verified: Limbach Company LP has Internal ID 7578, ID 69, and
it's 69 that appears on the order line); a project row has no usable
customer ID at all, so its customer text is matched by **exact string**
against the customer file's `Name` column, never `normalize_name`. All
152,988 lines resolved cleanly (100%). "Sold project" = every distinct
project text whose `Class = "Equipment Sales"` lines sum to more than
$100,000, all-time: **1,359 projects, $642,374,999 in equipment dollars**.

**Scout side.** Every `Project` row's `name` was run through
`app.normalize.normalize_name` — unchanged, this is project/signal
identity, not the company-identity function fixed elsewhere this session —
and compared for an exact match against the same function applied to the
NetSuite project text.

**Owner-token matching was attempted and rejected.** A second pass pulled
tokens (≥4 characters, filtered against a hand-built stoplist of ~40 generic
construction/real-estate words, and required to be rare enough — appearing
on at most 3 Scout projects — to plausibly identify one specific project)
from the NetSuite project name and matched them against tokens in the
Scout project's own name and `developer` field. It produced 446 "matches"
that are not trustworthy; §3 shows why with real examples. No amount of
stoplist tuning fixed the underlying problem, so this pass is **not**
reported as a match count anywhere in this document or the Phase B report
it came from.

## 3. Why the owner-token pass is not trustworthy

Two concrete failures, both from real output, not constructed examples:

- **"Apple CU99 – 1205 Colorado TI"** (an Apple Inc. facility job — "CU99"
  is an Apple building code, "TI" is tenant improvement) matched
  **"Apple Valley 84 Project"** on the shared token `apple` — but "Apple
  Valley" is a San Bernardino County city name. Same word, two unrelated
  referents.
- **"AREE ATC Building E Warm Shell"** matched **"LV Warm Springs Warehouse
  and Distribution Center"** on the shared token `warm` — "Warm Shell" is
  construction-industry jargon for a building shell with basic utilities;
  "Warm Springs" is a place name. Again, coincidental, not semantic.

Construction and real-estate naming conventions are dense with reused
jargon and place names short enough to survive any length/stoplist filter
that still lets real signal (a distinctive owner or place name) through.
There is no token-frequency threshold that separates "rare because it's
identifying" from "rare because English has a lot of words" at this sample
size. This is a dead end for this data shape, not a tuning problem.

## 4. Why address and lead time were not computable

- **Address:** `ScoutSalesOrderLinesResults612.csv` carries no address field
  on any line — only `Internal ID`, `Document Number`, `Date`, `Status`,
  `Name`, `Sales Rep`, `Item`, `Quantity`, `Amount`, `Class`, `Department`,
  `Customer Category`, `Customer PO #` (×2). The customer file's billing
  address is the contractor's office, not the job site, and using it as a
  stand-in would produce a false sense of a working join rather than a real
  one, so it wasn't used.
- **Lead time** (first Scout signal date − first NetSuite order date) is
  only meaningful for a trustworthy match. With 0 exact-name matches and no
  reportable owner-token matches, there is nothing to measure it from.
- **Retrofit board overlap**: also downstream of having a real match set.
  Separately worth noting for whenever a real match set exists:
  `app.models.RetrofitBuilding`'s own class docstring already documents
  zero APN overlap between `retrofit_buildings` and `projects` as a known,
  pre-existing structural fact — any future check here needs to go through
  address, not APN.

## 5. Conclusion

**Scout's board and DMG's sold history are different populations, not a
naming mismatch waiting on better fuzzy matching.** Sampling NetSuite's own
"data center"-named jobs shows they are overwhelmingly *service, repair,
and replacement* work at already-built, long-standing facilities — SCE
Alhambra, Amgen, Disney, Warner Bros., USC, SDG&E among them (19 such
project names found, all equipment-service framed: "Repair," "Startup,"
"Resiliency," unit-tag-specific line items). Scout's pipeline is built to
find *new-construction* data-center/industrial leads from public
entitlement filings (CEQA notices, agenda items) months to years before
ground is broken. DMG's actual $642M of >$100k sold equipment work over
this period is, by the top-20 list in §2, dominated by hospitals, schools,
tenant improvements, and government/aviation repair — none of which CEQA
entitlement filings are the right source for.

This does not mean Scout is wrong for what it targets, and it does not mean
DMG's sold history is invisible to public records — it means the specific
overlap this backtest went looking for (a Scout-sourced lead converting
into one of these NetSuite orders) essentially doesn't exist in the data
checked here. If validating Scout's lead value against DMG's own win
history matters going forward, the right population to check is Scout's
*new-construction data-center/industrial* leads against DMG's *new-
construction* NetSuite orders specifically — a much smaller, more
targeted comparison than "everything over $100k," and one this session did
not attempt.
